# Phase 7 Plan — Trend Analysis (Stage 7)

Requirements: TREND-01, TREND-02. README §8 Stage 7 / §15 Phase 7.
**Tech fixed by the spec: Pandas + NumPy.** No model, no network, no external
service: this phase reads persisted Phase 6 rows and writes derived rows.

## Starting position

`app/trends/` holds only `__init__.py`. Phase 6 is complete and frozen: the
`clusters` / `cluster_members` / `cluster_contradictions` tables exist, and
`app.clustering.storage.list_clusters` + `members_for_cluster` are its published
read API. Every member row already carries the `year` Phase 5 copied out of
`papers.year`, so Stage 7's whole input is already in PostgreSQL.

Phase 6's known DeBERTa-MNLI false-positive characteristic stays an open design
question and is **not** touched here.

## Contracts pinned by surviving code (must not change)

From `app/api/routes_backend.py` (`GET /trends`, `POST /trends`,
`POST /pipeline/run`) and `frontend/src/types.ts` + `TrendChart.tsx`:

- `app.trends.storage.list_trends(session)` → rows exposing `.cluster_id: int`,
  `.yearly_counts`, `.slope: float`.
- `app.trends.service.rebuild_trends(session)` → `list[int]`. Called with the
  session only, in both places. The caller commits, so this flushes and never
  commits.
- `yearly_counts` is serialized straight into the JSON response and the
  dashboard types it as `Record<string, number>`, reading it as
  `trend.yearly_counts[String(year)] ?? 0` and summing `Object.values(...)`.
  **Keys must therefore be year strings and values ints.**
- `slope` is a plain number the dashboard sorts on and renders `.toFixed(2)`.
- Phase 8 consumes the same value as its `trend_slope` signal
  (`gap_score = ... + w2*trend_slope ...`), so it must be a signed
  mentions-per-year rate, not a normalized or clipped score.

## Decisions

### D-07-01 — a "mention" in a year is a *distinct paper*, not a statement

README §8 Stage 7 states the unit in its own example — *"'Hallucination': 5
papers in 2021 → 140 in 2025"* — and §8 Stage 9's evidence line reads *"27
papers mention it"*. Counting cluster *members* instead would let one paper that
contributed four limitation sentences to a cluster register four mentions in one
year, manufacturing both frequency and slope out of a single publication. That
is the same failure D-06-04 already rejected on the contradiction side (a paper
disagreeing with itself is an extraction artefact). So each cluster's members are
de-duplicated by `paper_id` within a year before counting.

### D-07-02 — interior years with no mentions are filled with zero

A cluster mentioned in 2020 and 2023 has a series of `2020, 2021, 2022, 2023`
with `0` in the two middle years, not a two-point series. The zeros are the
literal truth (nobody mentioned it those years) and they are what makes the
slope a rate *per year* rather than per observation; dropping them would make a
dormant theme look as steep as an accelerating one. Filling is bounded to the
cluster's own observed `[min_year, max_year]` — never extrapolated outward,
which would invent evidence about years the corpus says nothing about.

### D-07-03 — undated members are excluded, not bucketed

A member whose `year` is `NULL` came from a paper with no publication year (a
manual upload GROBID could not date). It cannot be placed on a time axis, and
inventing a year for it would put fabricated evidence into a Phase 8 signal. It
is excluded from the series and logged in aggregate. It still counts as a
cluster member for `Cluster.member_count`, which is Phase 8's separate
`mention_frequency` input — this phase does not touch that.

### D-07-04 — a bounded, configurable sanity window on years

Metadata noise (`year = 12`, `year = 12345`) survives ingestion. With D-07-02
zero-filling, one such value turns a five-year series into a several-thousand-
entry dict and flattens the slope toward zero. `TREND_MIN_YEAR` (default 1900)
and `TREND_MAX_YEAR` (default 2100) bound the window in central settings per
CLAUDE.md; a member outside it is dropped exactly like an undated one. Both
bounds are static constants rather than "now", because a slope that changed
value with the wall clock would not be reproducible.

### D-07-05 — ordinary least squares over (year, count), computed in closed form

`slope = sum((x-xbar)*(y-ybar)) / sum((x-xbar)^2)` over the zero-filled series,
evaluated with NumPy. Units are **mentions per year**, signed. Chosen over
`np.polyfit`, which emits a `RankWarning` and returns unstable coefficients on
the degenerate inputs this phase must handle routinely, and over any
normalization, which would bake a scaling choice into Phase 8's `w2`.

Degenerate cases all resolve to a defined `0.0`, never `NaN`:

| series | slope |
|---|---|
| empty (no datable member) | `0.0` |
| one year | `0.0` — the denominator is zero; a single point has no rate |
| flat (every year equal) | `0.0` — the numerator is zero |

### D-07-06 — the stored slope is rounded to 6 decimal places

Least-squares on float64 leaves a bottom-bit tail that differs across BLAS
builds. Six decimals is far below any weight Phase 8 could give it and above any
resolution the dashboard renders (`.toFixed(2)`), and it makes "the same corpus
produces the same number" checkable rather than aspirational.

### D-07-07 — one row per cluster, always, in a separate wipe-and-rewrite table

Phase 7's "done when" is *each cluster has a time series and a trend score*, so a
cluster with nothing datable gets a row with `{}` and `0.0` rather than no row —
otherwise Phase 8 would have to distinguish "not computed" from "no trend".

`cluster_trends` is its own table with `cluster_id -> clusters.id ON DELETE
CASCADE`, not a column on `clusters`: Phase 6 replaces the `clusters` table
wholesale on every rebuild, so cluster ids are not stable and a trend must be
recomputed after clustering, not carried along with it. The cascade is what stops
a bare `POST /clusters` on PostgreSQL from failing on a foreign key. SQLite does
not enforce foreign keys by default, so `replace_trends` also deletes every
existing row itself before inserting — the same belt-and-braces
`replace_clusters` already uses.

## Tasks (TDD — failing test first for each)

1. **`tests/trends/test_analysis.py` -> `app/trends/analysis.py`**
   Pure computation, no DB. `TrendSeries` dataclass; `build_series(members)`
   (pandas de-dup + `groupby` + `reindex` zero-fill, window filtering);
   `trend_slope(series)` (NumPy closed form). Covers: normal multi-year growth,
   decline, sparse interior gaps, single year, flat series, empty, duplicate
   papers in one year, `None` years, out-of-window years, ascending key order,
   string keys / int values, determinism under input reordering.
2. **`tests/trends/test_storage.py` -> `app/trends/storage.py`**
   `ClusterTrend` ORM row + `replace_trends` + `list_trends`. Covers: round-trip
   of `yearly_counts` through the JSON column with keys still strings, wipe-and-
   rewrite (no accumulation across rebuilds), deterministic `cluster_id` order,
   flush-not-commit, empty input.
3. **`tests/trends/test_service.py` -> `app/trends/service.py`**
   `rebuild_trends(session, settings=None)` over real persisted Phase 6 rows.
   Covers: one row per cluster including empty ones, returned ids, no clusters →
   `[]`, idempotence across two runs, settings window honoured.

   `cluster_trends` must be on `Base.metadata` after importing `app.main`, the

6. **`app/core/config.py`** — `trend_min_year` / `trend_max_year` + validator;
   `tests/core/test_config.py` additions. **`backend/pyproject.toml`** — declare
   `pandas`.
