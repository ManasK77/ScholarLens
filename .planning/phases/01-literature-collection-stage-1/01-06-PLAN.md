<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> POST /collect {topic} | Untrusted string, passed to three external search APIs and used only as a query parameter, never as a URL/path/SQL fragment |
| Client -> POST /upload (multipart PDF) | Untrusted binary content and untrusted client-supplied filename/content-type header |
| routes_ingestion.py -> corpus.py/dedup.py | Internal, trusted call path — no additional validation needed beyond what corpus.py/dedup.py already enforce |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-12 | Tampering | Path traversal via `UploadFile.filename` in `/upload` | mitigate | `manual_upload.save_upload` never derives the on-disk path from the client filename — always a server-generated `{paper_id}.pdf` (Task 1, D-12) |
| T-01-13 | Denial of Service | Oversized/zip-bomb-style PDF upload | mitigate | `MAX_UPLOAD_SIZE_MB` enforced via `len(file_bytes)` check before any disk write; rejected with 413 |
| T-01-14 | Tampering | Content-type spoofing (non-PDF file sent with `Content-Type: application/pdf`) | accept | D-18 only specifies content-type-header rejection; magic-byte (`%PDF-`) verification flagged in RESEARCH.md as a recommended hardening but out of this plan's locked scope — revisit if abuse is observed |
| T-01-15 | Denial of Service | `/collect`'s topic string triggering unbounded fan-out across 3 external APIs + Unpaywall per DOI | accept | Each source module already applies conservative retry/timeout defaults (Plans 01-02/01-03/01-04/01-05); no additional rate-limiting added here per CONTEXT.md's explicit "not a designed feature" scoping |
| T-01-16 | Elevation of Privilege | `/collect`/`/upload` are unauthenticated | accept | API-key auth is explicitly Phase 11's scope (API-02); these endpoints are internal/local-dev-scale in this phase, matching Phase 0's `/health` precedent |

</threat_model>
