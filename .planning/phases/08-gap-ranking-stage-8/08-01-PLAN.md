# Phase 8 Plan — Gap Ranking (Stage 8)

Requirements: GAPRANK-01, GAPRANK-02. README §8 Stage 8 / §15 Phase 8.
**Tech fixed by the spec: plain Python — "no ML model, a transparent weighted
formula".** No model, no network, no vector store: this phase reads persisted
Phase 3/6/7 rows plus `papers`, and writes derived rows.

## Starting position

`app/ranking/` holds only `__init__.py`. Phases 6 and 7 are complete and frozen:

- `clusters` / `cluster_members` / `cluster_contradictions` (Phase 6), read
  through `list_clusters` + `members_for_cluster`.
- `cluster_trends` (Phase 7), read through `list_trends`. D-07-07 guarantees
  **one row per cluster**, so a missing trend means a bug, not "no data".
- `extracted_facts` (Phase 3), read through `app.extraction.storage`.
- `papers` (Phase 1).

Phase 6's known DeBERTa-MNLI false-positive characteristic stays an open design
question and is **not** touched here.

## Prerequisite defect work (authorized with this phase)

### P5 — fact point ids are not stable across pipeline runs

Reproduced, not assumed (`/tmp/repro2.py`, two papers, two runs):

```
paper1 fact db id run1/run2: 1 3     point id stable: False
paper2 fact db id run1/run2: 2 4     point id stable: False
```

`indexer._record_id("fact", paper.id, str(fact.id))` keys the Qdrant point on
`ExtractedFact.id` — a **database surrogate key**. `replace_facts` is
delete-then-insert, so every run mints fresh autoincrement ids for the same
statements. A second `POST /pipeline/run` therefore writes a *new* point for
every fact and orphans the previous one, and `gap_points()` returns each
limitation N times after N runs. That inflates Phase 6 `member_count` and would
inflate Phase 8's `mention_frequency`.

The module docstring already claims the invariant this violates: *"Point ids are
`uuid5` of a stable `kind:paper_id:position` key."* Paragraph ids honour it
(structural `section:paragraph` position); fact ids do not.

**Fix (smallest change consistent with the existing architecture):** key the
fact point on the fact's *natural evidence identity* — the same tuple the
`uq_extracted_fact_evidence` constraint already uses to define what makes two
facts the same row: `fact_type:section_index:paragraph_index:sentence_index:text`.
Same `uuid5`, same upsert, same payload; only the `position` string changes.

**Plus a bounded self-heal:** a stable key stops *new* orphans but cannot clear
the ones an already-run corpus contains. After a paper's records are
successfully upserted, delete that paper's points that are not in the current
record set (`paper_id == N AND NOT has_id(current)`). Scoped to a paper we just
indexed, so an unrelated failure can never wipe good vectors; cleanup failures
are logged, never fatal, so they cannot cost a paper its indexed count.

Phase 5's semantics (what is indexed, what the payload carries, cosine config,
batching) and Phase 6's semantics are otherwise untouched.

### P1 — `papers.citation_count` does not exist

`w4·citation_impact` has no input: the column is absent from the `Paper` model,
yet `routes_backend._paper_dict` reads `paper.citation_count` and
`frontend/src/types.ts` declares `citation_count: number | null`. `GET /papers`
would raise `AttributeError` today. Adding the nullable column fixes that
pre-existing contract break **and** is the minimum needed for Phase 8's fourth
signal to be anything but permanently zero.

Populated from Semantic Scholar (`citationCount` added to the existing `FIELDS`
string, mapped in `_to_paper_dict`) — README §7 names Semantic Scholar as the
source of "citation counts". `dedup.merge` is fill-if-None, so an arXiv record
later matched to an S2 record picks the count up and never loses it. No new
source, no new request, no branch on `source`.

## Contracts pinned by surviving code (must not change)

From `app/api/routes_backend.py` (`GET /gaps`, `POST /gaps`,
`POST /pipeline/run`) and `frontend/src/types.ts` + `App.tsx`:

- `app.ranking.service.rebuild_rankings(session, settings=None)` → `list[int]`.
  Called as `rebuild_rankings(session)` and `rebuild_rankings(session, settings)`
  — settings is the **second positional** parameter. The caller commits, so this
  flushes and never commits.
- `app.ranking.storage.list_rankings(session, limit)` → rows exposing
  `.cluster_id: int`, `.score: float`, `.mention_frequency`, `.trend_slope`,
  `.solution_density`, `.citation_impact`, `.contradiction_flag`.
- `GET /gaps` serializes those five under a `signals` object. `App.tsx` numbers
  the rows `index + 1` and calls them "Ranked research gaps", so
  **`list_rankings` must return best-first**; `limit` bounds the payload.
- `contradiction_flag` is typed `number` in `types.ts` and read for truthiness,
  so it is stored and served as `0.0`/`1.0`, not a boolean.
- The ranking table must declare `ForeignKey("clusters.id")` so Phase 6's
  `_dependent_tables()` discovers it and a bare `POST /clusters` cannot leave a
  ranking attached to a recycled cluster id (the Phase 7 review finding).

## Decisions

### D-08-01 — the formula is implemented literally, with raw per-cluster signals

```
gap_score = w1·mention_frequency + w2·trend_slope − w3·solution_density
          + w4·citation_impact  + w5·contradiction_flag
```

No cross-cluster normalization. Normalizing would make a cluster's score depend
on which *other* clusters happened to be in the run, so the same evidence would
score differently between runs and the Stage 9 sentence "27 papers mention it,
only 3 propose mitigations → score X" would stop being derivable from the
cluster's own numbers. Each signal stays in its natural unit and the weights are
what put them on a common scale — which is exactly what README §8's
"weights are configurable" is for. The stored breakdown is the raw values, so
every score is auditable by hand.

### D-08-02 — `mention_frequency` is distinct papers, not member statements

Same unit as Phase 7's D-07-01 and README §8 Stage 9's evidence line ("27 papers
mention it"). `Cluster.member_count` counts *statements*, so one paper that
contributed four limitation sentences would register four mentions. Counting
distinct `paper_id` also keeps this signal correct independently of the P5
defect above — belt and braces, since the root cause is fixed as well.

### D-08-03 — `trend_slope` is Phase 7's stored slope, used signed and unscaled

Read straight off `cluster_trends.slope`. Phase 7 already fixed the unit
(signed mentions per year), rounded it for reproducibility, and normalized
`-0.0`. Re-deriving or rescaling it here would fork the number the dashboard
plots from the number the score uses. A cluster with no stored trend scores
`0.0` — defensive only; D-07-07 guarantees a row per cluster.

### D-08-04 — `solution_density` matches contributions against the cluster label

*"papers proposing solutions ÷ papers mentioning the problem"*.

The denominator is unambiguous: the cluster's distinct papers (D-08-02).

The numerator needs "does this paper propose something for *this* theme", and
the only non-LLM, non-model evidence in the store is Phase 3's `contribution`
statements. The theme's own vocabulary is already computed, stored and
displayed: `Cluster.label` — Phase 6's deterministic document-frequency term
selection (D-06-06). So a paper proposes a solution when one of its
`contribution` facts contains **every** term of the cluster's label, matched
case-insensitively on word boundaries.

Reusing the stored label rather than re-deriving terms here keeps Phase 8 free
of `sklearn`/`numpy` (README fixes "plain Python"), avoids duplicating Phase 6's
stopword list, and makes the match auditable against something the user can
already see in the dashboard.

**The numerator is corpus-wide, not restricted to the cluster's papers.** A
paper that actually solved the problem does not usually list it as its own
limitation, so it is not in the cluster; restricting the numerator to cluster
members would make this signal ~0 for every theme and hand `w3` nothing to do.
The ratio is clamped to `[0, 1]` so the `− w3·density` term stays bounded, and
`1.0` reads as "at least as many papers contribute to this theme as complain
about it".

Degenerate cases resolve to `0.0`, never a division error: a cluster with no
label (nullable by Phase 6 contract) and a cluster with no papers.

### D-08-05 — `citation_impact` is the mean citation count of the mentioning papers

Mean, not sum: a sum is a second copy of `mention_frequency` (a 40-paper theme
outranks a 5-paper theme on citations because it has more papers, not more
impact), and `w1` already prices frequency.

An unknown count (`NULL` — an arXiv or ACL record never matched to a Semantic
Scholar result) counts as `0`. Dropping unknowns instead would let a single
known paper set the whole theme's impact; treating unknown as no-evidence-of-
impact is conservative and deterministic.

### D-08-06 — `contradiction_flag` is the flag, at 0.0 / 1.0

README names a *flag*, and `Cluster.contradiction_flag` is the boolean Phase 6
stores. `Cluster.contradiction_score` stays what it is — the audit value behind
the flag, already exposed on `GET /clusters` — and is deliberately not
substituted here: a 0.71 and a 0.99 contradiction are both "these papers
disagree", and swapping in the score would silently re-weight `w5` by the NLI
model's confidence.

### D-08-07 — default weights, and why they are what they are

Five settings, `gap_weight_mention_frequency` … `gap_weight_contradiction`,
bounded `>= 0` (the formula's own sign carries the direction of each term — a
negative weight would invert a signal's meaning behind the operator's back).

| weight | default | reading |
|---|---|---|
| w1 mention_frequency | 1.0 | one point per mentioning paper — the reference unit |
| w2 trend_slope | 3.0 | growing by one paper/year is worth three mentioning papers |
| w3 solution_density | 25.0 | a fully-addressed theme loses 25 points |
| w4 citation_impact | 0.02 | 50 mean citations ≈ one mentioning paper |
| w5 contradiction | 5.0 | a flagged cross-paper disagreement ≈ five mentioning papers |

`w3` is large on purpose: `solution_density` is a ratio in `[0, 1]` while
`mention_frequency` is an unbounded count, so a small `w3` would make the one
signal that says *"this is already being solved"* decorative. It is the term
most likely to want tuning per corpus, which is why README made the weights
configurable.

### D-08-08 — the stored score is rounded to 6 decimal places

Same reasoning as D-07-06: a float tail below any weight's significance, well
above the two decimals `formatScore` renders, and it keeps a re-run
byte-identical. `-0.0` is normalized to `0.0`.

### D-08-09 — ordering is by score, ties broken by cluster id

A rank the dashboard prints as "1, 2, 3" must not depend on row insertion order.
Descending score, then ascending `cluster_id`.

### D-08-10 — one row per cluster, always, wiped and rewritten

`cluster_rankings`, a derived table like Stage 6's and Stage 7's:
`cluster_id → clusters.id ON DELETE CASCADE`, unique, plus an explicit wipe in
`replace_rankings` (SQLite does not enforce foreign keys). Every cluster gets a
row — a cluster that scores `0.0` scored zero, it was not skipped.

## Task order (TDD — red, then green, per task)

1. **P5 regression tests** — fact point ids survive re-extraction; a second
   `index_all` over the same corpus leaves the same point set; stale points from
   a prior id scheme are pruned. Then fix `indexer.py`.
2. **P1** — `Paper.citation_count` column + Semantic Scholar mapping, with tests.
3. **Settings** — five weights, bounds, `.env.example`, `test_config.py`.
4. **`app/ranking/signals.py`** — each signal as a pure function over plain
   inputs, tested independently (GAPRANK-01's "test each signal term
   independently"), plus `gap_score` combining them.
5. **`app/ranking/storage.py`** — `ClusterRanking`, `replace_rankings`,
   `list_rankings`, table registration in `app/main.py`.
6. **`app/ranking/service.py`** — `rebuild_rankings(session, settings=None)`
   wiring Phases 3/6/7 reads to signals to storage.
7. **API contract test** — `GET /gaps` / `POST /gaps` / `POST /pipeline/run`
   projection, by the `ast` technique Phase 7 used while `routes_backend`
   remains unimportable.
8. Full suite, Ruff, code review, PROGRESS.md.
